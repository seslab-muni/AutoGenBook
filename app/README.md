# AutoGenBook Studio (frontend)

Vite + React 19 (strict TypeScript) frontend for AutoGenBook, on TanStack Router,
TanStack Query, Zustand, and shadcn/ui on Tailwind 4. It talks to the FastAPI
service in `../api/` and is served by nginx in the Docker Compose stack (see the
root `CLAUDE.md`).

Routing, a typed API/data layer, and the app shell (auth guard stub, Zustand
UI store, three-pane Structured Architect layout, theme toggle) are wired up,
and real screens are built on top of them against the live API: a projects
hub (`src/routes/index.tsx` → `src/features/projects`), per-project
source/outline/editor/run views (`src/routes/p.$projectId*.tsx` →
`src/features/{sources,outline,editor,runs}`), and export handling
(`src/features/exports`). See `src/features/<projects|sources|outline|editor|runs|exports>`
for the current feature set and their component tests for coverage.
`app/_reference/` holds the previous AI-Studio-exported mock UI, kept purely
as a layout/styling reference; it is excluded from `tsc`, ESLint, Vitest and
the Docker image, and will be deleted in #23 — don't add new code there.

## Prerequisites

- Node.js 22+ (Docker builds on `node:22-alpine`; also verified on Node 26)
- pnpm 11 (`corepack enable` will pick up the pinned version from
  `package.json`'s `packageManager` field)

## Scripts

```bash
pnpm install        # install dependencies
pnpm dev             # start the Vite dev server on :3000
pnpm gen:api         # regenerate src/api/schema.gen.ts from ../docs/openapi.yaml
pnpm lint            # eslint + tsc --noEmit
pnpm format          # prettier --write .
pnpm format:check    # prettier --check .
pnpm test            # vitest (watch mode)
pnpm test:ci         # vitest run (single pass, for CI)
pnpm build           # tsc -b && vite build -> dist/
pnpm preview         # preview the production build locally
```

Re-run `pnpm gen:api` (and commit the result) in the same PR whenever
`docs/openapi.yaml` changes — `src/api/schema.gen.ts` is generated, not
hand-edited.

## Environment / proxying

Copy `.env.example` to `.env` to override the defaults:

- `VITE_API_BASE_URL` — base URL the API client (`src/api/client.ts`) prepends
  to spec paths, which already carry the full `/api/v1/...` prefix. Defaults to
  the page's own origin, relying on the proxy below to route `/api/*` to the
  backend; only set this to point at a different host entirely.
- `VITE_API_PROXY_TARGET` — target for the Vite dev-server's `/api/*` proxy
  (`vite.config.ts`), so `pnpm dev` can talk to a locally running `api/` service.
  Defaults to `http://localhost:8080`. In the Docker Compose stack, nginx
  (`nginx.conf.template`) proxies `/api/` to the `api` container instead.
- `VITE_USE_MOCKS` — set to `1` to run `pnpm dev` entirely against the in-browser
  MSW mock API (`src/mocks/`) instead of a real backend; unset/`0` uses
  `VITE_API_PROXY_TARGET`.

## Folder layout

```
src/
  app/          # providers (QueryClientProvider, RouterProvider) and the router/query-client setup
  routes/       # TanStack Router file-based routes only — thin, no business logic
  features/     # one folder per feature area (components, hooks, queries):
                #   projects, sources, outline, editor, runs, exports
  api/          # typed API client: schema.gen.ts, client.ts, types.ts, upload.ts, sse.ts, queries/
  stores/       # Zustand stores — one small, focused store per concern
  components/
    ui/         # shadcn/ui primitives, generated by `pnpm dlx shadcn add ...` — don't hand-edit
  components/   # shared, hand-written components (not feature- or route-specific)
  lib/          # framework-agnostic helpers (e.g. `cn()` in lib/utils.ts)
  auth/         # session.ts + require-auth.ts — anonymous-session stub until real auth lands
  test/         # Vitest setup (`test/setup.ts`) and shared test utilities
  mocks/        # MSW request handlers + fixtures, backing both `pnpm dev` (VITE_USE_MOCKS=1) and Vitest
  routeTree.gen.ts   # generated by @tanstack/router-plugin — committed, don't hand-edit
```

Routes stay thin: a route module owns params/search-param parsing, loader
wiring, and rendering a feature's top-level component — the actual UI and data
logic live under `src/features/<name>`.

## API client layer

`src/api/schema.gen.ts` is generated from `../docs/openapi.yaml` by
`openapi-typescript` (`pnpm gen:api`) — every DTO type in the app is a
re-exported alias of a generated type (`src/api/types.ts`), never
hand-written, so they cannot drift from the spec. `src/api/client.ts` wraps
`openapi-fetch` in a single `apiClient`, an `ApiError` (`{status, problem,
url}`) for non-2xx/network failures, and an `unwrap()` helper every query
function calls. `src/api/queries/<resource>.ts` exposes `queryOptions()`
factories (`projects`, `sources`, `outline`, `runs`, `files`) plus
`useXxxMutation` hooks with hierarchical query keys (`src/api/queries/keys.ts`)
so invalidating a project cascades to its sources/outline/runs.
`src/api/upload.ts` posts files via `XMLHttpRequest` (for upload-progress
events `fetch` doesn't have); `src/api/sse.ts`'s `subscribeRunEvents` follows a
run's SSE stream and falls back to polling after repeated connection errors.

`src/mocks/` backs both `VITE_USE_MOCKS=1 pnpm dev` and every Vitest run
(wired in `src/test/setup.ts`, which reseeds the in-memory store before each
test): MSW handlers for every endpoint in the spec, fixtures ported from
`_reference/data/sampleBooks.ts`, and `src/mocks/fakeRun.ts`, which drives a
newly created run through `queued → running → succeeded`, emitting
`stage`/`log`/`section`/`done` events like the real worker would.

## shadcn/ui workflow

`components.json` points the `shadcn` CLI at this project (`new-york` style,
`slate` base color, CSS variables, `@/*` → `src/*`). To add a component:

```bash
pnpm dlx shadcn@latest add <component>
```

This drops the component into `src/components/ui/` using the `cn()` helper
from `src/lib/utils.ts` (not the generated `cn` import some CLI versions default
to — components are patched to `import { cn } from "@/lib/utils"` so there is a
single, hand-maintained implementation). Generated files under
`src/components/ui/` are excluded from ESLint (`eslint.config.js`) since they're
vendor code refreshed by the CLI, not hand-edited.

Known caveat: a handful of Radix-based components (`context-menu`,
`dropdown-menu`, `slider`, `sonner`) fail `tsc` under this project's
`exactOptionalPropertyTypes: true` the moment something actually imports them,
because some Radix prop types aren't `exactOptionalPropertyTypes`-clean.
`dropdown-menu` and `sonner` are now wired up (app shell, #16) and patched
accordingly; when a later issue first imports `context-menu` or `slider`,
apply the same fix to their failing prop passthrough — avoid passing an
explicit `undefined` for an optional prop (e.g.
`{...(value !== undefined ? { value } : {})}` instead of `value={value}`), and
prefer casting to the prop's own literal union type over an indexed type like
`SomeProps["theme"]`, which includes `undefined` for any optional property
regardless of the cast value.

## Design tokens

`src/index.css` maps the AutoGenBook palette (indigo primary, slate neutrals,
emerald/amber/sky/rose semantic colors) onto shadcn's CSS-variable tokens, adds
`--font-sans` (Plus Jakarta Sans), `--font-serif` (STIX Two Text / Crimson Pro,
for manuscript content), and `--font-mono` (JetBrains Mono) as Tailwind
`@theme` entries, and self-hosts all four via `@fontsource-variable/*` packages
(no Google Fonts `<link>`). Dark mode uses Tailwind 4's `class` variant
(`.dark` on an ancestor) with a full token set already defined in
`src/index.css`. `next-themes` (`ThemeProvider` in `app/providers.tsx`) owns
theme state — it applies/removes the `dark` class, resolves `system` against
the OS preference, and persists the choice to `localStorage` — rather than the
Zustand UI store, so `sonner`'s `Toaster` (which reads theme via
`next-themes`' `useTheme()`) stays in sync for free.
`components/layout/theme-toggle.tsx` is the toggle UI.

## Testing

Vitest + `@testing-library/react`, `jsdom` environment. `src/test/setup.ts`
starts the MSW `server` (`src/mocks/server.ts`), reseeds its in-memory
database before every test, and polyfills `window.matchMedia` (jsdom lacks
it; `next-themes` queries it for `system` theme detection).
`src/test/msw-polyfills.ts` runs first (a `setupFiles` entry of its own) to
polyfill `EventSource`, which jsdom lacks and MSW's `sse()` handler
feature-detects at import time. `src/test/router-test-utils.tsx`'s
`renderRouterApp(path)` renders the real, MSW-backed route tree inside a
memory-history router — used by `src/test/smoke.test.tsx` (provider stack,
routing, the project-not-found path) and by route/component tests that need a
real router context (e.g. `src/components/layout/app-header.test.tsx`'s
project switcher); `src/api/queries/*.test.ts` exercise the query/mutation
layer against the real MSW handlers, and `src/api/{client,sse,upload}.test.ts`
cover the lower-level transport pieces (the latter two against fakes — see
comments in those files for why real transports don't survive Node/jsdom's
interop with MSW here).
